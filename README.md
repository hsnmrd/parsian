# گزارش تراکنش‌ها

این پروژه برای تسک فنی Frontend Developer پیاده‌سازی شده است. صفحه اصلی پروژه در مسیر `/transaction` قرار دارد و اطلاعات را از یک API آزمایشی شامل ۶۰۰ تراکنش ثابت دریافت می‌کند.

## امکانات

- جست‌وجو براساس نام مشتری، شماره کارت یا شناسه تراکنش
- فیلتر وضعیت و بازه زمانی
- صفحه‌بندی سمت سرور همراه با `totalCount`
- شبیه‌سازی تأخیر شبکه
- نمایش جدول در دسکتاپ و کارت در موبایل
- حالت‌های Loading، Empty و Error
- نگهداری فیلترها و صفحه‌بندی در URL

## فناوری‌ها

- Next.js 16، React 19 و TypeScript
- Tailwind CSS و shadcn/ui
- TanStack Query و micro-rq برای داده‌های سرور
- nuqs برای وضعیت URL
- Zod برای اعتبارسنجی داده‌ها

## راه‌اندازی

```bash
pnpm install
cp .env.example .env.local
pnpm dev
```

سپس آدرس [http://localhost:3000/transaction](http://localhost:3000/transaction) را باز کنید.

برای بررسی کیفیت پروژه:

```bash
pnpm lint
pnpm exec tsc --noEmit
pnpm format:check
pnpm build
```

## سناریوهای خواسته‌شده

### ۱. درخواست‌های هم‌زمان

برای هر `useQuery`، یک `Observer` در `TanStack Query` ثبت می‌شود. با تغییر `queryKey`، این `Observer` از `Query` قبلی جدا و به `Query` جدید متصل می‌شود. اگر `Query` قبلی دیگر هیچ `Observer` فعالی نداشته باشد، درخواست آن از طریق `AbortSignal` لغو می‌شود. نتیجه هر درخواست نیز در cache کلید خودش قرار می‌گیرد؛ بنابراین پاسخ قدیمی نمی‌تواند داده فیلتر جدید را بازنویسی کند. برای جلوگیری از ارسال درخواست‌های زیاد به سمت سرور، جست‌وجو با تأخیر ۴۵۰ میلی‌ثانیه‌ای انجام می‌شود.

### ۲. مشکلات واقعی حل‌شده در توسعه

#### نمایش اولیه و LCP

- **مشاهده:** با وجود ثابت بودن عنوان و فیلترها، نمایش اولیه صفحه تا دریافت پاسخ API به تأخیر می‌افتاد.
- **روش مشاهده مشکل:** بارگذاری صفحه با تأخیر شبیه‌سازی‌شده API در تب Performance مرورگر ضبط و زمان نمایش محتوای اصلی بررسی شد.
- **فرضیه‌ها:** فونت محلی، حجم JavaScript یا منتظر ماندن Server Component برای prefetch می‌توانستند عامل تأخیر باشند.
- **بررسی:** trace مرورگر با مسیر رندر کد مقایسه شد. صفحه پیش از برگرداندن JSX منتظر `queryClient.query` می‌ماند؛ بنابراین پوسته ثابت نیز همراه نتایج مسدود می‌شد.
- **علت اصلی:** وابستگی کل صفحه به درخواست async نتایج، مرز مناسبی برای streaming باقی نمی‌گذاشت.
- **رفع:** پوسته ثابت صفحه بیرون `Suspense` قرار گرفت و فقط بخش نتایج با Skeleton به‌صورت streaming بارگذاری شد.
- **شواهد:** در ضبط بعد از تغییر، عنوان و فیلترها پیش از پایان درخواست API نمایش داده شدند و Skeleton فقط فضای نتایج را پوشش داد.

#### عملکرد تقویم

- **مشاهده:** تعامل با انتخاب‌گر تاریخ، مخصوصاً در موبایل، با تأخیر پاسخ می‌داد.
- **روش مشاهده مشکل:** تعامل با تقویم در تب Performance مرورگر ضبط و معیار INP همراه با بخش‌های Input Delay، Processing و Presentation بررسی شد.
- **فرضیه‌ها:** انیمیشن باز شدن پنجره، دریافت اطلاعات از سرور یا هزینه رندر تقویم فارسی می‌توانستند عامل کندی باشند.
- **بررسی:** سهم اصلی INP مربوط به Processing بود. انتخاب تاریخ فقط state موقت تقویم را تغییر می‌داد و درخواست API یا تغییر URL نداشت؛ بنابراین مسیر رندر تقویم بررسی شد.
- **علت اصلی:** ساخت هم‌زمان شبکه روزهای تقویم و تکرار محاسبات کلاس‌ها و قالب‌بندی تاریخ، main thread را هنگام تعامل درگیر می‌کرد.
- **رفع:** ابتدا Skeleton سبک نمایش داده شد و mount تقویم یک فریم عقب افتاد؛ کلاس‌های پیش‌فرض و `Intl.DateTimeFormat` نیز یک‌بار در سطح ماژول ساخته شدند.
- **شواهد:** در بررسی مجدد Performance، باز شدن کنترل از ساخت کامل تقویم جدا شد؛ ابتدا Drawer یا Popover و Skeleton نمایش داده شدند و تقویم در فریم بعد ساخته شد.

#### مقادیر خارج از محدوده در URL

- **مشاهده:** کاربر می‌توانست مقادیری مانند `page=-1`، `page=999` یا `pageSize=0` را مستقیماً در URL وارد کند و state خارج از محدوده بسازد.
- **روش مشاهده مشکل:** مقادیر `page=-1`، `page=999`، `pageSize=0` و `pageSize=101` به‌صورت دستی در URL قرار گرفتند و صفحه refresh شد.
- **فرضیه‌ها:** اعتبارسنجی فقط در UI انجام می‌شد، یا Client و Route Handler قوانین متفاوتی برای این مقادیر داشتند.
- **بررسی:** مقدارها در سه مرز parser مربوط به nuqs، schema مربوط به Zod و محاسبه صفحه در Route Handler دنبال شدند.
- **علت اصلی:** URL یک ورودی خارجی است و تعداد کل صفحات نیز فقط پس از فیلتر شدن داده‌ها در سرور مشخص می‌شود؛ بنابراین اتکا به مقدار خام URL کافی نبود.
- **رفع:** مقادیر نامعتبر `page` و `pageSize` با Zod به مقدار پیش‌فرض برمی‌گردند و Route Handler شماره صفحه بزرگ‌تر از محدوده را به آخرین صفحه معتبر محدود می‌کند. مقدار URL عمداً بازنویسی نمی‌شود.
- **شواهد:** `page=-1` صفحه اول، `page=999` آخرین صفحه و `pageSize=0` یا `pageSize=101` اندازه پیش‌فرض را نمایش دادند؛ هیچ‌کدام باعث خطا یا Empty state اشتباه نشدند.

#### جست‌وجو با اعداد فارسی

- **مشاهده:** جست‌وجوی شماره کارت یا شناسه با اعداد فارسی نتیجه درستی نمایش نمی‌داد، در حالی که همان مقدار با اعداد انگلیسی پیدا می‌شد.
- **روش مشاهده مشکل:** عبارت‌هایی مانند `۶۰۳۷۹۹`، `٦٠٣٧٩٩` و `۱۰۱۲۳` در فیلد جست‌وجو وارد شدند و با نسخه انگلیسی همان عبارت‌ها مقایسه شدند.
- **بررسی:** مقدار جست‌وجو به‌درستی در URL ثبت و به API ارسال می‌شد، اما مقایسه با شماره کارت و شناسه‌های ذخیره‌شده با ارقام انگلیسی انجام می‌گرفت.
- **علت اصلی:** اعداد فارسی و عربی از نظر Unicode با اعداد انگلیسی متفاوت‌اند و مقایسه رشته‌ای آن‌ها برابر نیست.
- **رفع:** یک تابع خالص برای تبدیل اعداد فارسی و عربی به انگلیسی ساخته شد و در `transactionFilterSchema` به‌عنوان transform فیلد `search` قرار گرفت. متن input و URL تغییر نمی‌کند و فقط مقدار مصرف‌شده در Query و API نرمال می‌شود.
- **شواهد:** تبدیل مقادیر فارسی، عربی و ترکیبی مانند `603۷۹۹` تست شد و همه آن‌ها پیش از جست‌وجو به مقدار انگلیسی یکسان رسیدند.

### ۳. تغییر فیلتر در صفحه ۸

با تغییر جست‌وجو، وضعیت یا بازه زمانی، مقدار `page` به `1` برمی‌گردد. در غیر این صورت ممکن است تعداد صفحات نتیجه جدید کمتر باشد و کاربر اشتباهاً یک صفحه خالی ببیند. Route Handler نیز شماره صفحه خارج از محدوده را نرمال می‌کند.

## پاسخ کوتاه به سؤال‌های تحلیلی

### چرا کامپوننت‌ها به این شکل تقسیم شده‌اند؟

چون پروژه فقط یک قابلیت اصلی دارد، ساختار route-first ساده‌تر و خواناتر از feature-first است. کامپوننت‌های عمومی در `src/components/ui` قرار گرفته‌اند تا قابل استفاده مجدد باشند و اجزای مخصوص تراکنش نزدیک مسیر خود نگهداری می‌شوند. نمایش موبایل و دسکتاپ نیز به‌دلیل تفاوت ساختاری کارت و جدول از هم جدا شده‌اند. منطق خالص، فرمت‌کننده‌ها و schemaها بیرون کامپوننت‌ها هستند تا تست و نگهداری آن‌ها ساده‌تر باشد.

### محل نگهداری `state` کجاست؟

- فیلترها و صفحه‌بندی: `nuqs` و URL
- داده، cache و وضعیت درخواست: TanStack Query
- وضعیت‌های موقت رابط، مانند باز بودن Drawer: `useState`

این تقسیم‌بندی نیاز به یک store سراسری جداگانه را حذف می‌کند. فیلترها نیز در URL نگهداری می‌شوند تا لینک صفحه با همان تنظیمات قابل اشتراک‌گذاری باشد و کاربر مستقیماً به نتیجه فیلترشده دسترسی پیدا کند.

### درخواست‌های هم‌زمان چگونه مدیریت می‌شوند؟

برای هر `useQuery`، یک `Observer` ثبت می‌شود. با تغییر فیلتر، این `Observer` به `queryKey` جدید متصل می‌شود و اگر `Query` قبلی دیگر استفاده‌کننده‌ای نداشته باشد، درخواست آن با `AbortSignal` لغو می‌شود. نتیجه هر درخواست نیز در cache کلید خودش باقی می‌ماند و پاسخ قبلی نمی‌تواند داده فیلتر جدید را بازنویسی کند.

### اگر API واقعی سه ثانیه زمان پاسخ داشته باشد چه می‌شود؟

استفاده از تأخیر کوتاه در جست‌وجو، نمایش `Skeleton` بدون جابه‌جایی چیدمان، نگهداری cache با `staleTime` مناسب، لغو درخواست قبلی و پیش‌بارگذاری صفحه بعد، زمان انتظار را قابل‌فهم‌تر می‌کند. داده کامل قبلی برای فیلتر جدید نمایش داده نمی‌شود تا نتیجه قدیمی با نتیجه در حال بارگذاری اشتباه نشود.

### در سیستم با ۲۰ میلیون تراکنش، مسئولیت Backend و Frontend چیست؟

- مسئولیت Backend: فیلتر، جست‌وجو، مرتب‌سازی، ایندکس‌گذاری و صفحه‌بندی داده‌ها و ارسال فقط صفحه موردنیاز همراه با `totalCount`.
- مسئولیت Frontend: ارسال فیلترها و اطلاعات صفحه به سرور، نگهداری آن‌ها در URL، نمایش وضعیت‌های مختلف و مدیریت درخواست‌ها؛ شامل استفاده از cache و تأخیر جست‌وجو برای جلوگیری از درخواست‌های اضافی و لغو درخواست‌های قدیمی.

### چه بخش‌هایی عمداً ساده نگه داشته شده‌اند؟

- پارامتر نامعتبر کاربر در URL بازنویسی نمی‌شود؛ برای نمونه `page=999` در URL باقی می‌ماند، اما آخرین صفحه معتبر نمایش داده می‌شود.
- لغو `fetch` در کلاینت انجام می‌شود، اما `sleep` شبیه‌ساز تأخیر در Mock API با signal متوقف نمی‌شود؛ چون حجم درخواست‌ها کم است و تمرکز پروژه روی رفتار Frontend قرار دارد.
- به‌جای دیتابیس و سرور جدا، از Route Handler خود Next.js و یک مولد داده deterministic استفاده شده است.
- استفاده از Redux یا Zustand ضروری نبود، چون URL، React Query و state محلی نیاز پروژه را پوشش می‌دهند.

## استفاده از هوش مصنوعی

در طول توسعه از **Antigravity** و **Codex** برای بررسی مستندات، گرفتن پیشنهاد در بعضی بخش‌ها، تنظیم ابزارهای کیفیت و بازبینی کد استفاده کردم. برای پیاده‌سازی رابط کاربری نیز با هدایت و بررسی خودم از هوش مصنوعی کمک گرفتم. در ابتدای کار به Codex دسترسی شخصی نداشتم؛ به همین دلیل بعضی بخش‌ها با Antigravity پیش رفتند. بررسی Performance نیز در پایان کار و پس از تکمیل پروژه و بازبینی کلی کد انجام شد. هیچ خروجی‌ای بدون بررسی وارد پروژه نشد.

پیشنهادهای AI که رد یا اصلاح شدند:

- ساختار feature-first برای این پروژه تک‌فیچری بیش از حد پیچیده بود؛ ساختار route-first در `src/app/transaction` انتخاب شد.
- رندر هم‌زمان نسخه موبایل و دسکتاپ با CSS `hidden` باعث ورود هر دو نسخه به مسیر رندر و bundle می‌شد؛ به‌جای آن از media query و dynamic import استفاده شد.
- مرتب‌سازی داخل `seed-data` پذیرفته نشد؛ داده Mock خام باقی ماند و sort در Route Handler، پیش از pagination، انجام شد.
- استفاده از `keepPreviousData` و `Spinner` برای تغییر نتایج کنار گذاشته شد و یک `Skeleton` مشترک برای همه حالت‌های بارگذاری استفاده شد تا داده قدیمی با نتیجه جدید اشتباه نشود.
- نگهداری جداگانه متن جست‌وجو با `useState` و `useEffect` لازم نبود؛ debounce خود nuqs و URL به‌عنوان منبع اصلی وضعیت حفظ شدند.
